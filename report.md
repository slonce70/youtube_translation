# Звіт про стан стрімінгового бекенду

## Поточна реалізація

- **FFmpeg-команди** (`backend/app/streaming/ffmpeg_manager.py:209`):
  - Одна дестинація: `ffmpeg -re -stream_loop -1 -f concat … -c:v copy -c:a copy -bsf:v h264_mp4toannexb -f flv <uri>`. Потік повторюється нескінченно, мінімальне навантаження на CPU, все тримається на попередній валідації H.264/AAC/yuv420p.
  - Декілька дестинацій: `tee` із ре-енкодом (`libx264`/`aac`) плюс той самий `-stream_loop -1`. Забезпечує сумісні FLV-теги, але бітрейт відео плаває (CRF за замовчуванням).
- **Плейлисти** (`backend/app/streaming/playlist_builder.py:47`): файл `ffconcat version 1.0` із абсолютними шляхами. Параметр `loop` поки не використовується, нескінченність забезпечує тільки `-stream_loop -1` у команді.
- **Управління статусом** (`backend/app/api/routes/streams.py:313`): при старті БД-статус стає `running`, зберігається PID і шлях до логу. `_monitor_process` (`backend/app/streaming/ffmpeg_manager.py:263`) при exit=0 просто очищає кеші в менеджері, але **не оновлює** рядок у БД, тому UI бачить «running» навіть після зупинки. `total_duration_seconds` теж не накопичується при нормальному завершенні.
- **Обробка помилок**: `_handle_stream_failure` створює `SystemAlert` і, залежно від `ffmpeg_auto_restart_attempts`, перезапускає процес. Логи stderr пишуться асинхронно (`_write_logs_to_file`).
- **Очищення**: є `cleanup_dead_streams`, але не викликається автоматично — після збою воркера можливі «висячі» процеси в памʼяті менеджера.

## Виявлені проблеми та ризики

1. **БД-статус не синхронізований** з фактичним станом процесу. UI не знає, що стрім завершився, кнопка залишається в «Stop».
2. **Відлік тривалості** (`total_duration_seconds`) оновлюється тільки під час аварій в `_mark_stream_failed`.
3. **Плейлисти із `'` у шляху** розваляться, бо рядок `file 'path'` не екранує апостроф.
4. **Відсутній резервний cleanup**: якщо `_monitor_process` не спрацює (креш воркера), словники менеджера не очищаються.
5. **Мультикаст без контрольованого бітрейта**: CRF може йти вище YouTube-рекомендацій, що веде до «пиляних» потоків.
6. **UI** (`frontend/src/app/dashboard/streaming/page.tsx:226`): полінг `/streams` кожні 3 с, але без фіксу з боку БД статус не оновиться; відсутній показ `uptime`, історії падінь, індикації авто-ресурту.

## Рекомендації

- Додати фіналізацію у `_monitor_process`: оновлювати `Stream.status`, `stopped_at`, `pid=None`, накопичувати `total_duration_seconds` для будь-якого завершення (manual stop, exit=0, failure).
- Винести це в окремий хелпер `_finalize_stream(record, status, message=None)` і викликати також із `_mark_stream_failed`.
- Додати фонове завдання (наприклад, у `startup_event`) для періодичного `ffmpeg_manager.cleanup_dead_streams()`.
- Для мультикасту зафіксувати бітрейт (`-b:v`, `-maxrate`, `-bufsize`), можливо, `-tune zerolatency`. Перевірити навантаження на CPU.
- У `PlaylistBuilder` екранувати `'` в шляхах або використовувати `Path.as_posix()` + правильне екранування.
- На фронті після бекенд-фіксів розширити відображення: `uptime`, позначки авто-ресурту, історія помилок (через `SystemAlert`).

## Дослідити додатково

1. Гайдлайни YouTube щодо bitrate ladder, keyframe ≤2 с, warmup, резервний ingest (`rtmps://b.rtmp.youtube.com`).
2. Health-check потоку: відстеження поточного бітрейта, drop frames, попередження користувача до того, як YouTube обірве стрім.
3. Порівняння з конкурентами: нескінченні плейлисти (дехто формує `.ts`), вебсокети для статусу, автоматичні резервні трансляції.
4. Політика перезапусків (`ffmpeg_auto_restart_attempts`) і backoff — чи достатньо поточних значень (1 спроба, 5 с), чи потрібна гнучка конфігурація.

## Висновок

Основна логіка потоків працює: FFmpeg запускається, цикл безкінечний, логи пишуться, авто-ресурт передбачений. Головний вузол болю — відсутність оновлення статусу в БД при нормальному завершенні, що вводить в оману фронтенд та білінг. Після синхронізації станів і незначних правок (cleanup, бітрейти, екранування шляхів) система стане набагато надійнішою й прозорішою для користувачів.
