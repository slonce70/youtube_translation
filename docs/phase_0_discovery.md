# Фаза 0 — дискавері та узгодження

## 1. Аудит поточної схеми та пайплайнів

### 1.1 Модель активів і плейлистів
- `assets` зберігає базову інформацію про файли (шлях у файловій системі, розмір, тривалість), а також витягнуті параметри кодеків і валідаційний статус, що підтягується з ffprobe та перевірок пайплайна.【F:backend/app/models/database.py†L84-L115】【F:backend/app/api/routes/assets.py†L149-L197】
- `playlists` групує активи через `playlist_items`, підтримує порядок відтворення і прапорець `loop`, а також звʼязується зі стрімами через `Stream.playlist`.【F:backend/app/models/database.py†L121-L155】

### 1.2 Стріми та прямі привʼязки активів
- `streams` можуть працювати у двох режимах: читати активи з плейлиста (`source_type=playlist`) або з власної черги `stream_assets` (`source_type=assets`), паралельно маючи список призначень через `stream_destinations` та журнал подій.【F:backend/app/models/database.py†L192-L271】
- API вибирає активи для запуску стріму або з плейлиста, або з `stream_assets`, формуючи структурований список з порядком і метаданими для побудови плейлиста FFmpeg.【F:backend/app/api/routes/streams.py†L31-L200】

### 1.3 tusd-хуки й життєвий цикл завантаження
- `pre-create` хук перевіряє наявність `user_id`, викликає внутрішній `/api/internal/check-quota` з HMAC-підписом і за потреби блокує завантаження, а також створює користувацьку директорію в storage.【F:backend/tusd-hooks/pre-create†L1-L115】
- `post-finish` переносить файл із `_temp` у директорію користувача, оновлює шлях у пейлоаді та шле webhook у бекенд на `/api/assets/upload-complete` для подальшої обробки та створення запису активу.【F:backend/tusd-hooks/post-finish†L1-L113】【F:backend/app/api/routes/assets.py†L149-L197】

### 1.4 Формування плейлистів і запуск FFmpeg
- `PlaylistBuilder` збирає concat-файл (`ffconcat version 1.0`) із абсолютними шляхами до активів, перевіряє існування файлів і може виконувати валідацію сумісності кодеків для direct copy.【F:backend/app/streaming/playlist_builder.py†L11-L200】
- `FFmpegStreamManager` будує команди: для одного призначення використовує `-c copy` і FLV теги, для кількох — tee-мультиплексор з перекодуванням у `libx264/aac`, а також веде моніторинг процесу та при збої ініціює обробку помилок.【F:backend/app/streaming/ffmpeg_manager.py†L203-L320】

## 2. User-flow ключових сценаріїв

### 2.1 Відео-фон для стріму
1. Користувач ініціює завантаження через tusd; `pre-create` викликає бекенд для перевірки квоти згідно з тарифом робочої області (від 3 ГБ на free до сотень гігабайт на платних планах) і готує директорію.【F:backend/tusd-hooks/pre-create†L24-L115】【F:backend/migrations/013_update_tariffs.sql†L21-L79】【F:tariff.md†L22-L56】
2. Після завершення завантаження `post-finish` переносить файл, надсилає webhook; бекенд створює запис активу, збагачуючи його метаданими для подальших перевірок.【F:backend/tusd-hooks/post-finish†L35-L113】【F:backend/app/api/routes/assets.py†L149-L197】
3. Користувач додає актив у плейлист або напряму до стріму. API підтягне повʼязані активи в правильному порядку для побудови concat-файлу.【F:backend/app/api/routes/streams.py†L51-L200】
4. `PlaylistBuilder` формує текстовий плейлист, після чого `FFmpegStreamManager` запускає трансляцію з копіюванням кодеків або перекодуванням залежно від кількості цілей.【F:backend/app/streaming/playlist_builder.py†L11-L200】【F:backend/app/streaming/ffmpeg_manager.py†L203-L320】

### 2.2 Аудіо-плейлист для міксу
- Поточна схема не розділяє тип активу, тому аудіоконтент обробляється як звичайний `asset`; майбутнє введення `asset_type` та окремих колекцій закладене у плані фази 1, що дозволить формувати незалежні аудіо-черги.【F:backend/app/models/database.py†L84-L115】【F:plan.md†L8-L31】
- Для MVP користувач створює плейлист лише з аудіо-файлів; стрім у режимі `playlist` дає доступ до `playlist.items`, що дозволяє будувати окремий аудіо-плейлист та міксувати його з відео в майбутньому.【F:backend/app/api/routes/streams.py†L51-L200】

### 2.3 Віртуальні папки та теги
- У плані заплановано структуру `media_folders` і `asset_folder_links`; на дискавері-етапі підтверджуємо, що сьогоднішня модель не містить ієрархії, тому потрібні нові таблиці та UI для переміщення активів між папками.【F:plan.md†L8-L31】
- Необхідно забезпечити масові дії (переміщення, фільтри All/Video/Audio) та синхронізувати їх з правами доступу й квотами, що вже реалізовані для активів та плейлистів.【F:plan.md†L44-L54】【F:backend/app/api/routes/assets.py†L125-L233】

### 2.4 Сценарії видалення
- Видалення активу наразі не перевіряє залежності: файл стирається з файлової системи й запис видаляється без попередження, що створює ризик «битих» стрімів/плейлистів.【F:backend/app/api/routes/assets.py†L642-L697】 Це критична точка для каскадних оновлень.
- Плейлисти мають запобіжник: бекенд блокує видалення, якщо стріми ще посилаються на плейлист, повертаючи `409 Conflict` з повідомленням.【F:backend/app/api/routes/playlists.py†L230-L288】
- Для майбутнього сервісу каскадних дій потрібно поверх наявної логіки фіксувати залежності в `SystemAlert` і на UI показувати, які стріми/плейлисти постраждають, перед підтвердженням видалення.【F:backend/app/models/database.py†L296-L320】【F:plan.md†L30-L31】【F:plan.md†L56-L64】

## 3. Граничні умови та дані для UI
- Актуальна тарифна матриця задає обмеження для кожного плану (наприклад, 3 ГБ сховища та 1 стрім для `free`, 50 ГБ і 1 стрім для `fhd_start`, до 800 ГБ і 4 стрімів для `uhd_boost`). Ці ліміти потрібно відображати у бібліотеці медіа (використання/залишок) та в конструкторі стріму (попередження перед стартом).【F:backend/migrations/013_update_tariffs.sql†L21-L79】【F:tariff.md†L22-L56】
- Для каскадних змін UI має відображати: плейлисти, у яких використовується актив (через `playlist.items`), стріми, які споживають плейлист або `stream_assets`, а також активні призначення. Усі ці звʼязки вже завантажуються в `_load_stream_with_relations`, тому API може згенерувати узагальнений список залежностей для фронтенду.【F:backend/app/api/routes/streams.py†L31-L115】
- Попереджувальні банери мають також дублюватися у `SystemAlert`, щоб адміністратори бачили деградацію конфігурації, коли користувач ігнорує рекомендації чи перевищує квоти.【F:backend/app/models/database.py†L296-L320】【F:plan.md†L30-L31】

## 4. Ризики, зафіксовані на етапі дискавері
- Поточне видалення активів без перевірок може «ламати» стріми; необхідний фоновий сервіс, що перебудовує колекції та створює алерти, як зазначено у плані фази 2–5.【F:backend/app/api/routes/assets.py†L642-L697】【F:plan.md†L30-L64】
- Відсутність типізації активів ускладнює розділення відео/аудіо плейлистів; міграції фази 1 мають додати `asset_type`, базові папки й backfill через ffprobe.【F:backend/app/models/database.py†L84-L115】【F:plan.md†L8-L18】
- Для підтримки майбутнього live-редагування потрібно розширити `FFmpegStreamManager` гарячими замінами; нинішня реалізація вже зберігає метадані процесу та веде історію помилок, що стане основою для feature flag'у hot swap.【F:backend/app/streaming/ffmpeg_manager.py†L210-L320】【F:plan.md†L33-L43】

Цей документ закриває фокус фази 0: ми зібрали звʼязки між основними сутностями та пайплайнами, окреслили кінцеві user-flow для ключових сценаріїв, підтвердили тарифні обмеження й окреслили, які дані потрібні UI для безпечних каскадних дій.【F:plan.md†L3-L7】
